1. Goal and scope

Given one or more local JavaScript entry files, report every statically reachable local ESM file, the import edges, its UTF-8 byte count, and one deterministic shortest path explaining why it is included. Provide a CLI JSON report and a local demo that compares those static facts with observed browser resource requests. A developer should be able to read the report and say, “suffix.js is present because main.js imports message.js, which imports suffix.js.”

4. Mandatory second artifact: the code implementation plan

Agent instruction: After reading this brief and auditing the repository, create docs/task-1-code-implementation-plan.html as a distinct artifact before editing application code. Then implement the approved scope and keep the code plan accurate if a justified design change is made. The code plan is part of Task 1's deliverables.

The code implementation plan must contain all of the following:

  1. Repository audit: actual current behavior, gaps versus this brief, Node/runtime constraints, dependencies already present, and decisions needed. Correct any mistaken assumptions from this brief using code evidence.
  2. Design contracts: precise graph schema and example JSON; path normalization and symlink policy; static import semantics; tie-breaking for inclusion paths; CLI errors and exit codes; HTTP routes and error states; browser observation versus inference.
  3. File-by-file matrix: every file to add or modify, its current responsibility, exact proposed functions/types/exports, algorithm or request flow, inputs and outputs, effect on other files, corresponding test IDs, and migration or compatibility concern. Include package.json, tests, fixtures, docs, and demo files when touched.
  4. Concrete code walkthrough: meaningful, syntactically plausible snippets for resolution/root checks, graph traversal, explanation paths, CLI error handling, server request routing, and browser rendering. Explain why each snippet exists and where it goes. Avoid vague placeholders such as “handle errors here.” Snippets are proposed code; final implementation may differ with an explained reason.
  5. Execution order: small changes in dependency order, with the test IDs run after each change. Identify any risky migration and how to recover if a test fails.
  6. Test implementation map: each ID above mapped to a test file, fixture, command, expected result, and whether it is automated or browser manual. Include a complete final command list and a browser verification checklist.
  7. Exit report format: final files changed, behavior changed, every test ID's result, actual commands and output summary, browser evidence, remaining limitations, and a truthful statement of whether Task 1 passed.
