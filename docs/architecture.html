Project brief · 4 October 2026

Build a bundler that explains itself

Module Atlas is a learning project and a potential developer tool: a modern ESM build pipeline with an evidence-backed explanation of which source modules became which chunks, and why the browser requested those chunks. Build correctness first, then measure performance.

Built now: slice 1

The repository includes a static JavaScript import graph, a JSON inclusion report, and a native ESM browser demo that records resource timing. It does not produce a bundled application yet. Run npm test, npm run inspect, and npm run demo.

1. What a bundler actually does

Start at one or more entries. Resolve each import to a file or package export. Parse the file, transform its syntax and assets, and recursively collect dependencies into a graph. Determine which code has observable effects and which exports are used. Partition the remaining graph into initial and lazy chunks, generate runtime-valid code, optionally minify it, and emit files plus a manifest. A development server can use the same graph while serving modules on demand.

These are design directions, not claims that Module Atlas outperforms any of these tools. Vite's implementation evolves; pin versions and consult current documentation during each comparison.

3. The differentiator: a causal build manifest

Each decision should leave a machine-readable record. An agent can query it, but the underlying evidence remains inspectable by a developer. The first JSON report already records static import edges and a shortest inclusion chain. Future versions will attach module, export, chunk, asset, route, and browser observation IDs.

{
  "module": "src/chart.tsx",
  "includedBy": ["src/main.tsx", "src/routes/reports.tsx"],
  "chunk": "reports.8b42.js",
  "reason": "dynamic import from reports route",
  "bytes": { "raw": 21800, "gzip": 6500 },
  "browser": { "observedOn": ["/reports"], "priority": "normal" },
  "evidence": ["import-edge:41", "chunk-decision:9"]
}

That example is a target schema sketch; the current graph JSON only contains entries, module sizes, imports, and shortest paths. An assistant might answer “why did this CSS load?” by tracing the CSS import or HTML link and the containing route. It should distinguish direct evidence from a suggestion such as “consider a lazy boundary.” Recommendations need reproducible before/after measurements, and the agent must never silently change chunk policy.

Build facts

Source imports, resolved IDs, used exports, side effect decisions, chunk membership, emitted bytes, build duration.

Browser observations

Navigation, resource start and duration, initiator type where provided, cache state and transfer size where exposed, preload or prefetch links.

Advice

Identify unusually large initial chunks, duplicated packages, eager imports behind infrequent routes, or prefetches unused in a measured session.

Why start with native ESM output? It gives a correctness baseline and exposes browser requests. Bundle concatenation, code splitting, tree shaking, and chunk loading can then be added without hiding semantic errors behind a custom runtime. React and Svelte support require framework transforms and plugin integration; they are explicit later milestones.

5. Technical decisions worth proving

  • Language and parser: Slice 1 is a small Node.js JavaScript prototype. Use TypeScript for the growing core from slice 2 onward: typed graph nodes, import edges, plugin contracts, and explanation records. The current experimental Node parser is temporary. A production parser must provide reliable syntax trees and source ranges; choose and benchmark candidates at slice 2. Rust is an option only if profiling identifies a meaningful bottleneck.
  • TypeScript: Browsers execute JavaScript. Fast syntax conversion can remove types without checking them. Run type checking separately so “the build passed” cannot imply the program is type safe.
  • Tree shaking: ESM names make usage analysis possible, but imports can execute side effects. Handle module and statement effects conservatively; never erase code because an export appears unused without proving that its evaluation is safe to omit.
  • Multiple entries: Track each entry's reachability and share a module only when shared chunks reduce total bytes and requests for the target navigation profile. Record the policy and estimated cost.
  • Prefetch: It is a browser hint for a possible future need, not proof of demand. Keep it opt-in until navigation traces justify it. Preload addresses current navigation dependencies and requires a separate decision.
  • Agent interface: Offer stable JSON and a CLI such as explain module, explain request, and compare builds. Include evidence IDs and confidence/unknown fields. Avoid sending source contents or browsing traces to any external service by default.

6. Performance claims need a protocol

Use the same source application, lockfile, browser, machine, target browsers, minification, source map settings, and cache state for each tool. Publish exact versions and commands. Repeat measurements, report medians and spread, and retain raw traces. Compare cold and warm dev startup, edit-to-screen latency, full production build duration, initial and route-specific transferred JS/CSS (raw and gzip), request count, and browser milestones such as LCP and INP where valid. A smaller bundle does not necessarily make a page faster; network conditions, parsing, execution, and caching matter.

Honest portfolio claim today: “Built a dependency graph inspector and browser request explainer for ESM, with cycle and error handling tests.” Once a real bundler exists, describe the exact supported feature set. Make any “faster than X” statement only after the published comparison reproduces it.
